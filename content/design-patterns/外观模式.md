# 外观模式 Facade

> **核心思想：**为一组复杂子系统提供一个面向具体业务场景的简单入口。

Facade 不是“把所有 Service 再包一层”。它应该表达一个**高层用例**，把调用顺序、错误处理和跨组件协作隐藏在内部。

## 场景：提交订单需要调用多个子系统

```text
Inventory
Payment
OrderRepository
Coupon
Notification
```

如果 HTTP Handler 自己编排：

```go
stock.Reserve(...)
payment.Charge(...)
orderRepo.Create(...)
coupon.Use(...)
notify.Send(...)
```

Controller 很快会变成真正的业务层。

## 用 CheckoutFacade 表达一个完整用例

```go
type CheckoutFacade struct {
    inventory InventoryService
    payment   PaymentGateway
    orders    OrderRepository
    events    EventPublisher
}

type CheckoutCommand struct {
    UserID string
    SKU    string
    Qty    int
    Amount int64
}

type CheckoutResult struct {
    OrderID       string
    TransactionID string
}

func (f *CheckoutFacade) Checkout(ctx context.Context, cmd CheckoutCommand) (CheckoutResult, error) {
    reservation, err := f.inventory.Reserve(ctx, cmd.SKU, cmd.Qty)
    if err != nil {
        return CheckoutResult{}, fmt.Errorf("reserve inventory: %w", err)
    }

    charged, err := f.payment.Charge(ctx, cmd.UserID, cmd.Amount)
    if err != nil {
        _ = f.inventory.Release(context.WithoutCancel(ctx), reservation.ID)
        return CheckoutResult{}, fmt.Errorf("charge payment: %w", err)
    }

    order := Order{
        ID:            newID(),
        UserID:        cmd.UserID,
        ReservationID: reservation.ID,
        TransactionID: charged.ID,
    }

    if err := f.orders.Create(ctx, order); err != nil {
        // 真实生产系统应把补偿设计成可重试工作流，而不是假设这里一定成功。
        _ = f.payment.Refund(context.WithoutCancel(ctx), charged.ID)
        _ = f.inventory.Release(context.WithoutCancel(ctx), reservation.ID)
        return CheckoutResult{}, fmt.Errorf("create order: %w", err)
    }

    _ = f.events.Publish(ctx, OrderCreated{OrderID: order.ID})

    return CheckoutResult{
        OrderID:       order.ID,
        TransactionID: charged.ID,
    }, nil
}
```

Handler 只需要：

```go
result, err := checkout.Checkout(r.Context(), cmd)
```

## Facade 不等于分布式事务解决方案

上面的例子故意展示了补偿，但真实系统要继续考虑：

- payment 成功、进程在写订单前崩溃怎么办？
- compensation 自己失败怎么办？
- 消息发布与数据库提交如何保持一致？

这些通常需要 Outbox、Saga、幂等、对账等机制。Facade 只负责**把用例入口收敛**，不会神奇地提供事务一致性。

## 测试调用顺序和失败语义

可以通过 fake 记录动作：

```go
type Recorder struct { Calls []string }
```

测试支付失败时确保执行：

```text
reserve -> charge(fail) -> release
```

而不是只断言 `err != nil`。

## 一个好的 Facade 应该有什么

- 方法名表达业务用例：`Checkout`、`ProvisionTenant`、`StartSession`；
- 参数是业务 Command，不暴露子系统 SDK 类型；
- 错误有明确上下文；
- 不把所有子系统所有方法原样转发出去。

## 和 Adapter 的区别

Adapter 解决**接口不兼容**；Facade 解决**调用复杂度**。

第三方支付 SDK 可以先经过 Adapter 变成 `PaymentGateway`，然后由 Checkout Facade 编排使用，两者非常适合一起出现。
