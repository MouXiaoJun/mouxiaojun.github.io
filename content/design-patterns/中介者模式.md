# 中介者模式 Mediator

> **核心思想：**让多个组件不要彼此直接依赖，而是通过一个中介者协作，减少网状耦合。

当 A 调 B、B 调 C、C 又回调 A 时，系统很快会变成“所有模块都认识所有模块”。Mediator 的目标是把协作协议集中到一个地方。

## 场景：用户注册后的跨模块动作

用户注册完成后：

```text
Profile 创建默认资料
Audit 写审计
Welcome 发送欢迎消息
CRM 同步客户
```

最差的方式是 `UserService` 直接 import 四个模块。

定义中介事件：

```go
type UserRegistered struct {
    UserID string
    Email  string
}

type Handler[T any] interface {
    Handle(ctx context.Context, event T) error
}

type Mediator[T any] struct {
    handlers []Handler[T]
}

func (m *Mediator[T]) Register(h Handler[T]) {
    m.handlers = append(m.handlers, h)
}

func (m *Mediator[T]) Publish(ctx context.Context, event T) error {
    for _, handler := range m.handlers {
        if err := handler.Handle(ctx, event); err != nil {
            return err
        }
    }
    return nil
}
```

各模块只实现自己的 handler：

```go
type CreateProfileHandler struct {
    profiles ProfileService
}

func (h CreateProfileHandler) Handle(ctx context.Context, e UserRegistered) error {
    return h.profiles.CreateDefault(ctx, e.UserID)
}
```

UserService 只告诉 mediator：

```go
if err := users.Create(ctx, user); err != nil {
    return err
}
return mediator.Publish(ctx, UserRegistered{UserID: user.ID, Email: user.Email})
```

## 同步 Mediator 的失败语义必须明确

上面的实现是 fail-fast：第三个 handler 失败，第四个不会运行。

真实项目要先决定：

- 所有 handler 必须成功？
- 部分失败允许主流程成功？
- 是否应该改成 Outbox + 消息队列？
- handler 是否能重复执行？

不要因为用了 Mediator 就假装事务问题不存在。

## Mediator vs Observer

两者经常长得很像。

- Observer 强调“一对多通知”：发布者不关心谁收到；
- Mediator 强调“组件之间的协作由中心对象组织”。

如果你的 `Mediator` 只是一个通用 pub/sub，它更接近 Observer/Event Bus。

## 不要做成 God Mediator

危险信号：

```text
mediator.UserService
mediator.OrderService
mediator.PaymentService
mediator.InventoryService
...
```

最终所有业务都搬到一个 5000 行中介者里，只是把耦合从模块之间挪到了中心。

好的 Mediator 管**交互协议**，不吞掉每个模块自己的业务规则。

## 适合场景

- GUI/组件系统；
- 模块间协作越来越网状；
- Command/Query Bus；
- 领域事件在进程内分发。

如果只有 A -> B 一条简单依赖，直接注入接口更清楚。
