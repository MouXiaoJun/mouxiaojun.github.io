# 享元模式 Flyweight

> **核心思想：**把大量对象中重复、不可变的“内部状态”抽出来共享，把每次请求不同的“外部状态”放在调用时传入。

享元模式在现代 Go 后端里不常以这个名字出现，但缓存编译结果、共享不可变规则、连接池等思路都能看到它的影子。

## 场景：规则表达式被重复编译

假设每个请求都有：

```text
user-agent pattern
path pattern
```

如果每个 session 都重新 `regexp.Compile`：

```go
type SessionRule struct {
    Pattern *regexp.Regexp
    UserID  string
}
```

十万 session 使用同一个表达式，就会重复占用编译和内存成本。

## 把可共享状态独立出来

```go
type CompiledRule struct {
    expr string
    re   *regexp.Regexp
}

func (r *CompiledRule) Match(value string) bool {
    return r.re.MatchString(value)
}
```

Factory 负责按 key 复用：

```go
type RuleFactory struct {
    mu    sync.RWMutex
    rules map[string]*CompiledRule
}

func NewRuleFactory() *RuleFactory {
    return &RuleFactory{rules: make(map[string]*CompiledRule)}
}

func (f *RuleFactory) Get(expr string) (*CompiledRule, error) {
    f.mu.RLock()
    rule := f.rules[expr]
    f.mu.RUnlock()
    if rule != nil {
        return rule, nil
    }

    compiled, err := regexp.Compile(expr)
    if err != nil {
        return nil, err
    }

    f.mu.Lock()
    defer f.mu.Unlock()

    // double check：可能有另一个 goroutine 已经完成编译。
    if existing := f.rules[expr]; existing != nil {
        return existing, nil
    }

    rule = &CompiledRule{expr: expr, re: compiled}
    f.rules[expr] = rule
    return rule, nil
}
```

每次请求变化的状态不放进 Flyweight：

```go
type MatchInput struct {
    UserID string
    Path   string
}

func Match(rule *CompiledRule, input MatchInput) bool {
    return rule.Match(input.Path)
}
```

```text
CompiledRule（内部状态） -> 大量请求共享
UserID / Path（外部状态） -> 每次调用传入
```

## 为什么共享对象最好不可变

如果 `CompiledRule` 允许调用方修改表达式：

```go
rule.expr = "new pattern"
```

所有共享者都会受到影响，并发也立刻复杂起来。

享元对象最理想的性质是：

- 初始化后不可变；
- 并发安全；
- 可以被大量调用者共享；
- key 能稳定标识其内部状态。

## Cache 失控也是问题

上面的 `rules map` 永不回收。如果表达式来自无限用户输入，就会变成内存泄漏式缓存。生产中需要根据场景考虑：

- 最大容量；
- LRU/LFU；
- TTL；
- metrics（hit/miss/size）；
- singleflight 防止同 key 并发重复构建。

享元模式不是“加一个 map 就完了”。

## 测试确实复用了对象

```go
func TestFactoryReusesRule(t *testing.T) {
    f := NewRuleFactory()

    a, err := f.Get(`^/api/`)
    if err != nil { t.Fatal(err) }
    b, err := f.Get(`^/api/`)
    if err != nil { t.Fatal(err) }

    if a != b {
        t.Fatal("expected shared flyweight")
    }
}
```

## 什么时候值得用

只有同时满足两点才值得认真考虑：

1. 对象数量非常大或构造非常贵；
2. 大量对象确实拥有可提取的重复不可变状态。

普通几十个 struct 不需要享元；先测内存和 CPU，再优化。
