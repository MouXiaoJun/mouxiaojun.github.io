# 职责链模式 Chain of Responsibility

> **核心思想：**把多个处理者串成一条链，每个处理者只负责自己能处理的部分，否则把请求交给下一个。

职责链适合“规则按顺序尝试、命中即结束”的场景：审批、鉴权、风控、异常降级、客服路由等。

## 场景：退款审批

小额退款自动通过，中额由组长审批，大额进入财务审核。

```go
type RefundRequest struct {
    OrderID string
    Amount  int64
}

type Decision struct {
    ApprovedBy string
}

type Handler interface {
    Handle(ctx context.Context, req RefundRequest) (Decision, bool, error)
}
```

`bool` 表示当前节点是否已经处理。

```go
type AutoApprove struct { Max int64 }

func (h AutoApprove) Handle(_ context.Context, req RefundRequest) (Decision, bool, error) {
    if req.Amount > h.Max {
        return Decision{}, false, nil
    }
    return Decision{ApprovedBy: "auto"}, true, nil
}

type TeamLeadApproval struct { Max int64 }

func (h TeamLeadApproval) Handle(ctx context.Context, req RefundRequest) (Decision, bool, error) {
    if req.Amount > h.Max {
        return Decision{}, false, nil
    }
    // 真实系统可以在这里创建人工审批任务。
    return Decision{ApprovedBy: "team-lead"}, true, nil
}
```

链本身：

```go
type Chain struct {
    handlers []Handler
}

func NewChain(handlers ...Handler) Chain {
    return Chain{handlers: handlers}
}

func (c Chain) Handle(ctx context.Context, req RefundRequest) (Decision, error) {
    for _, handler := range c.handlers {
        decision, handled, err := handler.Handle(ctx, req)
        if err != nil {
            return Decision{}, err
        }
        if handled {
            return decision, nil
        }
    }
    return Decision{}, errors.New("no refund handler accepted request")
}
```

使用：

```go
chain := NewChain(
    AutoApprove{Max: 1000},
    TeamLeadApproval{Max: 10000},
    FinanceApproval{},
)
```

## 链的顺序就是业务规则

如果把 `FinanceApproval` 放第一位，所有请求都会进入财务。职责链最危险的 bug 往往不是代码错误，而是**节点顺序配置错误**。

因此生产系统建议：

- 启动时打印最终链顺序；
- 配置驱动时做重复/缺失校验；
- 每个节点增加命中率 metrics；
- 用 table-driven tests 覆盖边界金额。

```go
func TestRefundChain(t *testing.T) {
    tests := []struct {
        amount int64
        want   string
    }{
        {500, "auto"},
        {1000, "auto"},
        {1001, "team-lead"},
    }
    // ...
}
```

## 和 Middleware 的关系

HTTP middleware 常写成：

```go
logging(auth(trace(handler)))
```

它更接近 Decorator，因为每一层通常都会继续调用 next。职责链则允许某个节点**直接终止，不再向后传递**。

现实里两种结构可以混合，不必强行贴标签；关键是理解“谁负责决定继续传递”。

## 什么时候适合

- 处理规则很多且顺序有意义；
- 每个节点职责独立；
- 节点可插拔或配置化；
- 某个节点处理成功后可以停止。

如果所有步骤都必须执行，那更像 Pipeline / Decorator，而不是职责链。
