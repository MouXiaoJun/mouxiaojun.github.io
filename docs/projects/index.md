# 开源项目

我更愿意把开源项目当作长期工程，而不是仓库数量。每个项目都从一个真实、反复出现的问题出发，并明确它的**正确性边界、失败路径和长期演进方向**。

## 项目地图

| 项目 | 解决的问题 | 当前阶段 |
|---|---|---|
| [distsync](distsync/) | Go 服务跨进程同步、租约、限流与主节点选举 | 持续维护 |
| [gomodulith](gomodulith/) | 模块化单体边界如何被发现、验证和文档化 | 持续构建 |
| [SpecRiot](specriot/) | 如何从 OpenAPI 自动发现 API 契约与状态流错误 | v0.2 Contract Fuzzing |

## 我关心的共同原则

```text
简单 API
   ↓
明确语义
   ↓
失败路径可解释
   ↓
测试与 CI 可重复
   ↓
长期兼容与演进
```

### 正确性优先

基础设施库最危险的状态不是“报错”，而是**看起来成功，实际上已经失去所有权、越过边界或违反契约**。因此项目会优先说明它保证什么、不保证什么。

### Go 风格

不照搬 Java 或 Python 的表面 API，而是利用 Go 的 `context.Context`、接口、组合、`go test`、包可见性和标准工具链重新设计。

### 可观测与可复现

运行时问题需要指标与 Trace，测试工具发现的失败必须能通过固定 Seed 或 Artifact 重放，架构违规必须能在 CI 中稳定复现。
