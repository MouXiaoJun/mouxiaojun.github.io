# 建造者模式 Builder

> **核心思想：**当一个对象的构造步骤很多、参数之间存在约束时，把“逐步收集参数”和“最终校验并创建对象”分开。

Go 中经常把 Builder 和 Functional Options 混在一起讨论。两者都在解决“构造参数太多”的问题，但 Builder 更适合**需要分阶段填写并在最后统一校验**的复杂对象。

## 一个参数爆炸的构造函数

```go
func NewWorker(
    name string,
    concurrency int,
    timeout time.Duration,
    retries int,
    queue string,
    deadLetterQueue string,
    metrics bool,
) *Worker
```

调用时：

```go
NewWorker("email", 16, 5*time.Second, 3, "mail", "mail-dlq", true)
```

只看这一行很难知道 `16`、`3`、`true` 分别代表什么，参数之间的关系也没地方表达。

## Builder：先收集，再 Build

```go
package worker

import (
    "errors"
    "fmt"
    "time"
)

type Worker struct {
    name       string
    concurrency int
    timeout    time.Duration
    retries    int
    queue      string
    dlq        string
}

type Builder struct {
    worker Worker
}

func NewBuilder(name string) *Builder {
    return &Builder{worker: Worker{
        name:        name,
        concurrency: 1,
        timeout:     5 * time.Second,
    }}
}

func (b *Builder) Concurrency(n int) *Builder {
    b.worker.concurrency = n
    return b
}

func (b *Builder) Timeout(d time.Duration) *Builder {
    b.worker.timeout = d
    return b
}

func (b *Builder) Retry(n int, deadLetterQueue string) *Builder {
    b.worker.retries = n
    b.worker.dlq = deadLetterQueue
    return b
}

func (b *Builder) Queue(name string) *Builder {
    b.worker.queue = name
    return b
}

func (b *Builder) Build() (*Worker, error) {
    w := b.worker

    if w.name == "" {
        return nil, errors.New("worker name is required")
    }
    if w.queue == "" {
        return nil, errors.New("queue is required")
    }
    if w.concurrency <= 0 {
        return nil, fmt.Errorf("concurrency must be positive: %d", w.concurrency)
    }
    if w.timeout <= 0 {
        return nil, errors.New("timeout must be positive")
    }
    if w.retries > 0 && w.dlq == "" {
        return nil, errors.New("dead letter queue is required when retry is enabled")
    }

    return &w, nil
}
```

使用：

```go
worker, err := worker.NewBuilder("email-delivery").
    Queue("email.jobs").
    Concurrency(16).
    Timeout(3 * time.Second).
    Retry(5, "email.jobs.dlq").
    Build()
if err != nil {
    return err
}
```

这里最有价值的是：

- 参数名字在调用点可见；
- 默认值集中；
- 跨字段约束集中在 `Build()`；
- `Worker` 创建后可以保持不可变。

## 为什么不直接暴露 setter

```go
w := &Worker{}
w.SetQueue("jobs")
w.SetRetries(5)
```

问题是调用方可能在对象“不完整”的时候就开始使用它，而且你很难回答：**什么时候这个对象才算合法？**

Builder 有明确边界：

```text
Builder（可以不完整） -> Build 校验 -> Worker（必须合法）
```

## Go 更常见的 Functional Options

如果参数之间没有复杂构建步骤，只是很多可选配置，Go 通常更偏爱 Functional Options：

```go
type Option func(*Worker) error

func WithConcurrency(n int) Option {
    return func(w *Worker) error {
        if n <= 0 {
            return errors.New("concurrency must be positive")
        }
        w.concurrency = n
        return nil
    }
}

func WithTimeout(d time.Duration) Option {
    return func(w *Worker) error {
        if d <= 0 {
            return errors.New("timeout must be positive")
        }
        w.timeout = d
        return nil
    }
}

func New(name, queue string, options ...Option) (*Worker, error) {
    w := &Worker{
        name:        name,
        queue:       queue,
        concurrency: 1,
        timeout:     5 * time.Second,
    }

    for _, option := range options {
        if err := option(w); err != nil {
            return nil, err
        }
    }
    return w, nil
}
```

调用：

```go
w, err := New(
    "email",
    "email.jobs",
    WithConcurrency(16),
    WithTimeout(3*time.Second),
)
```

## Builder 还是 Functional Options？

| 情况 | 推荐 |
|---|---|
| 少量必填参数 + 很多独立可选项 | Functional Options |
| 构建过程有明确阶段 | Builder |
| 字段之间有复杂依赖约束 | Builder |
| 希望复用一份半成品配置继续构建 | Builder |
| 只是 2～3 个参数 | 普通构造函数 |

## 测试重点应该是约束

```go
func TestBuilderRequiresDLQWhenRetryEnabled(t *testing.T) {
    _, err := NewBuilder("email").
        Queue("jobs").
        Retry(3, "").
        Build()

    if err == nil {
        t.Fatal("expected validation error")
    }
}
```

不要只测 getter/setter。Builder 真正承担的职责是**保证最终对象合法**。

## 常见误区

### 为简单对象套 Builder

```go
type User struct {
    ID   int64
    Name string
}
```

直接：

```go
User{ID: 1, Name: "Alice"}
```

最清楚。为了“用了设计模式”再写十几个 Builder 方法只会降低可读性。

### Build 后继续共享内部 slice/map

如果 Builder 可以被复用，`Build()` 返回对象时要注意引用类型是否需要 clone，否则后续修改 Builder 可能影响已经构建的对象。

## 一句话判断

> 如果你的核心问题是“创建哪种对象”，看工厂；如果核心问题是“怎么把一个复杂对象一步步构造合法”，看建造者。
