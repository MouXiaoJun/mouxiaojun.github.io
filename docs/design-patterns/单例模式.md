# 单例模式 Singleton

> **核心思想：**确保一个进程内某类资源只初始化一次，并为调用方提供稳定访问入口。

单例模式在 Go 里很常见，但也最容易被滥用。数据库连接池、只读配置、指标注册器这类“进程级共享资源”可能适合单例；业务 Service、Repository 则通常更适合显式依赖注入。

## 一个容易写错的版本

```go
var client *Client

func GetClient() *Client {
    if client == nil {
        client = NewClient()
    }
    return client
}
```

并发请求第一次同时进入时，可能构造多个实例，还存在数据竞争。给它外面套一层 `if client == nil` + mutex 的 double-checking，也很容易写错。

## Go 的首选：`sync.Once`

```go
package config

import (
    "os"
    "sync"
)

type Config struct {
    Env      string
    APIKey   string
    LogLevel string
}

var (
    once sync.Once
    cfg  *Config
)

func Instance() *Config {
    once.Do(func() {
        cfg = &Config{
            Env:      os.Getenv("APP_ENV"),
            APIKey:   os.Getenv("API_KEY"),
            LogLevel: os.Getenv("LOG_LEVEL"),
        }
    })
    return cfg
}
```

`sync.Once` 保证传入函数在整个进程生命周期内只执行一次，并处理了并发可见性问题。

## 初始化可能失败怎么办

现代 Go 可以使用 `sync.OnceValues` 把成功值和错误一起缓存：

```go
package database

import (
    "database/sql"
    "sync"

    _ "github.com/go-sql-driver/mysql"
)

var openDB = sync.OnceValues(func() (*sql.DB, error) {
    db, err := sql.Open("mysql", "user:pass@tcp(localhost:3306)/app")
    if err != nil {
        return nil, err
    }
    if err := db.Ping(); err != nil {
        _ = db.Close()
        return nil, err
    }
    return db, nil
})

func DB() (*sql.DB, error) {
    return openDB()
}
```

需要特别理解这里的语义：**第一次返回错误以后，这个错误也会被记住。** 如果你希望网络恢复后重试，就不能直接把初始化失败永久缓存成单例状态。

## 并发测试

```go
func TestInstanceReturnsSamePointer(t *testing.T) {
    const n = 100

    got := make(chan *Config, n)
    var wg sync.WaitGroup

    for i := 0; i < n; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            got <- Instance()
        }()
    }

    wg.Wait()
    close(got)

    first := <-got
    for item := range got {
        if item != first {
            t.Fatal("singleton returned different instances")
        }
    }
}
```

测试时最好再运行：

```bash
go test -race ./...
```

因为单例最常见的问题本身就是并发问题。

## 更 Go 的选择：依赖注入

很多时候你以为自己需要单例，其实只是需要“应用启动时创建一次”。

```go
type App struct {
    DB     *sql.DB
    Orders *OrderService
}

func NewApp(db *sql.DB) *App {
    repo := NewOrderRepository(db)
    return &App{
        DB:     db,
        Orders: NewOrderService(repo),
    }
}
```

在 `main()` 里只构造一次：

```go
func main() {
    db := mustOpenDB()
    app := NewApp(db)
    runHTTP(app)
}
```

这里仍然只有一个连接池，但没有全局变量。测试时可以轻松替换依赖，也不会发生不同测试共享全局状态的问题。

## 单例最麻烦的地方：测试

`sync.Once` 没有 Reset。下面这种测试经常很痛苦：

```go
func TestProductionConfig(t *testing.T) {}
func TestDevelopmentConfig(t *testing.T) {}
```

两个测试如果都依赖全局 `Instance()`，谁先执行会影响另一个。因此：

- 真正不可变的进程级设施，可以使用单例；
- 会根据测试输入变化的对象，不要塞进单例；
- 不要为了方便少传一个参数，就把普通业务依赖做成全局单例。

## 适合的场景

- Prometheus registry 之类进程级注册器；
- 初始化昂贵、生命周期等于进程、并发安全的只读对象；
- SDK 内部必须保证只注册一次的 hook；
- 连接池这类共享资源（但通常仍建议由 `main` 显式持有）。

## 不适合的场景

- 有用户/租户状态的对象；
- Service / Repository 只是为了“方便访问”；
- 需要在运行期间重载的配置；
- 初始化失败后必须自动重试的资源；
- 测试中需要频繁替换实现的依赖。

## Go 工程里的判断标准

问自己一句：

> **这个对象真的必须“全局唯一”，还是只需要“在 composition root 创建一次”？**

如果只是后者，依赖注入通常比单例更清楚。
