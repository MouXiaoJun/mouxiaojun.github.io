# 工厂模式 Factory Method

> **核心思想：**把“选择并创建哪一个具体实现”的逻辑集中到一个明确位置，业务代码只依赖稳定接口。

Go 没有 class constructor，工厂模式通常就是一个返回接口或具体类型的 `NewXxx` 函数。它真正解决的不是“少写一个 `&T{}`”，而是**把创建策略从使用者手里拿走**。

## 场景：统一通知服务

系统支持短信、邮件、Webhook。最差的写法是把分支散落在业务代码里：

```go
switch order.NotifyChannel {
case "email":
    // new smtp client
case "sms":
    // new sms client
case "webhook":
    // new http client
}
```

以后新增渠道，订单、退款、告警模块都要跟着改。

## 定义稳定契约

```go
package notify

import "context"

type Message struct {
    To      string
    Subject string
    Body    string
}

type Sender interface {
    Send(ctx context.Context, msg Message) error
}
```

具体实现只关心自己的协议：

```go
type EmailSender struct {
    smtp *SMTPClient
}

func (s *EmailSender) Send(ctx context.Context, msg Message) error {
    return s.smtp.Send(ctx, msg.To, msg.Subject, msg.Body)
}

type WebhookSender struct {
    client *http.Client
}

func (s *WebhookSender) Send(ctx context.Context, msg Message) error {
    // 省略编码细节
    return nil
}
```

## 工厂集中创建逻辑

```go
type Channel string

const (
    ChannelEmail   Channel = "email"
    ChannelWebhook Channel = "webhook"
)

type Dependencies struct {
    SMTP *SMTPClient
    HTTP *http.Client
}

func NewSender(channel Channel, deps Dependencies) (Sender, error) {
    switch channel {
    case ChannelEmail:
        if deps.SMTP == nil {
            return nil, errors.New("smtp client is required")
        }
        return &EmailSender{smtp: deps.SMTP}, nil

    case ChannelWebhook:
        if deps.HTTP == nil {
            return nil, errors.New("http client is required")
        }
        return &WebhookSender{client: deps.HTTP}, nil

    default:
        return nil, fmt.Errorf("unsupported notify channel %q", channel)
    }
}
```

业务层：

```go
sender, err := notify.NewSender(order.NotifyChannel, deps)
if err != nil {
    return err
}
return sender.Send(ctx, msg)
```

使用者只知道 `Sender`，不关心 SMTP/Webhook 客户端到底怎么组装。

## 工厂不一定非要 switch

插件数量变多时可以用 registry：

```go
type Builder func(Dependencies) (Sender, error)

type Factory struct {
    builders map[Channel]Builder
}

func NewFactory() *Factory {
    return &Factory{builders: make(map[Channel]Builder)}
}

func (f *Factory) Register(channel Channel, builder Builder) {
    f.builders[channel] = builder
}

func (f *Factory) Create(channel Channel, deps Dependencies) (Sender, error) {
    builder, ok := f.builders[channel]
    if !ok {
        return nil, fmt.Errorf("sender %q is not registered", channel)
    }
    return builder(deps)
}
```

初始化：

```go
factory.Register(ChannelEmail, func(deps Dependencies) (Sender, error) {
    return &EmailSender{smtp: deps.SMTP}, nil
})
```

这适合第三方插件、支付渠道、存储 provider 等需要可扩展注册的场景。

## 测试工厂而不是测试 switch 文本

```go
func TestFactoryCreatesEmailSender(t *testing.T) {
    deps := Dependencies{SMTP: &SMTPClient{}}

    sender, err := NewSender(ChannelEmail, deps)
    if err != nil {
        t.Fatal(err)
    }

    if _, ok := sender.(*EmailSender); !ok {
        t.Fatalf("unexpected sender type %T", sender)
    }
}

func TestFactoryRejectsUnknownChannel(t *testing.T) {
    _, err := NewSender(Channel("carrier-pigeon"), Dependencies{})
    if err == nil {
        t.Fatal("expected error")
    }
}
```

## Go 里什么时候根本不需要工厂

如果对象构造已经足够清楚：

```go
client := &Client{Timeout: 3 * time.Second}
```

再包一层：

```go
func NewClient() *Client { ... }
```

并不会自动变成有价值的设计模式。

工厂最值得出现的信号是：

- 创建哪种实现需要运行时决定；
- 创建过程需要注入多种依赖；
- 调用方不应该知道具体类型；
- 新实现会持续增加；
- 创建规则需要统一校验。

## 和抽象工厂的区别

工厂方法通常创建**一个产品接口**：

```text
Channel -> Sender
```

抽象工厂创建的是**一整组相互匹配的产品**：

```text
AWSFactory -> ObjectStore + Queue + SecretStore
```

如果只是“根据类型创建一个实现”，普通工厂通常已经足够。
