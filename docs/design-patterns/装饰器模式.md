# 装饰器模式 Decorator

> **核心思想：**不修改原对象，通过包一层实现动态叠加能力，并保持对外接口不变。

Go 标准库里有大量 Decorator 思维：`http.Handler` middleware、`io.Reader` 链、`http.RoundTripper` 包装器。

## 场景：给 HTTP Client 叠加日志与鉴权

`http.RoundTripper` 是天然的装饰器接口：

```go
type RoundTripper interface {
    RoundTrip(*Request) (*Response, error)
}
```

鉴权装饰器：

```go
type AuthTransport struct {
    Token string
    Next  http.RoundTripper
}

func (t AuthTransport) RoundTrip(req *http.Request) (*http.Response, error) {
    cloned := req.Clone(req.Context())
    cloned.Header = req.Header.Clone()
    cloned.Header.Set("Authorization", "Bearer "+t.Token)
    return t.next().RoundTrip(cloned)
}

func (t AuthTransport) next() http.RoundTripper {
    if t.Next != nil {
        return t.Next
    }
    return http.DefaultTransport
}
```

日志装饰器：

```go
type LoggingTransport struct {
    Next   http.RoundTripper
    Logger *slog.Logger
}

func (t LoggingTransport) RoundTrip(req *http.Request) (*http.Response, error) {
    start := time.Now()
    resp, err := t.Next.RoundTrip(req)

    status := 0
    if resp != nil {
        status = resp.StatusCode
    }

    t.Logger.InfoContext(req.Context(), "http client request",
        "method", req.Method,
        "host", req.URL.Host,
        "status", status,
        "duration", time.Since(start),
        "error", err,
    )
    return resp, err
}
```

组合时按顺序包裹：

```go
base := http.DefaultTransport

auth := AuthTransport{
    Token: os.Getenv("API_TOKEN"),
    Next:  base,
}

logging := LoggingTransport{
    Next:   auth,
    Logger: slog.Default(),
}

client := &http.Client{
    Transport: logging,
    Timeout:   5 * time.Second,
}
```

调用方仍然只是普通 `http.Client`。

## 顺序是 Decorator 的一部分

```text
Logging(Auth(Base))
```

和：

```text
Auth(Logging(Base))
```

观测到的请求可能不一样。重试、Tracing、Metrics、Auth 的顺序尤其要明确。

## Handler Middleware 也是同一模式

```go
type Middleware func(http.Handler) http.Handler

func Recover(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        defer func() {
            if recover() != nil {
                http.Error(w, "internal error", http.StatusInternalServerError)
            }
        }()
        next.ServeHTTP(w, r)
    })
}
```

```go
handler := Recover(Auth(Trace(orderHandler)))
```

这就是函数式 Decorator。

## 测试包装链

```go
type RoundTripFunc func(*http.Request) (*http.Response, error)

func (f RoundTripFunc) RoundTrip(r *http.Request) (*http.Response, error) {
    return f(r)
}

func TestAuthTransportAddsHeader(t *testing.T) {
    next := RoundTripFunc(func(req *http.Request) (*http.Response, error) {
        if got := req.Header.Get("Authorization"); got != "Bearer secret" {
            t.Fatalf("unexpected auth header %q", got)
        }
        return &http.Response{StatusCode: 200, Body: http.NoBody}, nil
    })

    transport := AuthTransport{Token: "secret", Next: next}
    req, _ := http.NewRequest(http.MethodGet, "https://example.com", nil)

    _, err := transport.RoundTrip(req)
    if err != nil {
        t.Fatal(err)
    }
}
```

## Decorator vs Proxy

两者结构都可能是“持有同接口对象并转发”。区别看意图：

- Decorator：**叠加职责**，通常可以多层组合；
- Proxy：**控制访问**，例如缓存、远程代理、权限、延迟加载。

## 常见误区

- middleware 层数无限增长，导致执行顺序不可理解；
- 装饰器偷偷改变核心业务语义；
- 每层都做大量 IO，导致链路延迟难以追踪。

好的 Decorator 应该职责小、顺序明确、可单测。
