# 原型模式 Prototype

> **核心思想：**当“创建一个对象”本身很贵时，不要每次从零开始构造；准备一个已经初始化好的原型，再复制它并修改少量差异。

原型模式在 Go 里最容易被误解成“会 `copy` 就行”。真正需要关注的是：**对象图里哪些数据可以共享，哪些必须深拷贝，以及复制后的对象能否独立修改。**

## 先看一个真实问题

假设一个风控服务启动时，要从数据库和远程配置中心加载一份规则模板：

```go
func LoadPolicy(ctx context.Context, tenantID string) (*Policy, error) {
    // 真实项目里可能包含数据库查询、RPC、规则编译、正则编译等昂贵操作。
    rules, err := loadRulesFromDB(ctx, tenantID)
    if err != nil {
        return nil, err
    }

    return &Policy{
        TenantID: tenantID,
        Rules:    rules,
        Labels:   map[string]string{"source": "database"},
    }, nil
}
```

如果每创建一个执行任务都重新调用 `LoadPolicy`，创建成本会被重复支付。

但如果简单写：

```go
copy := *template
```

也有坑：`slice`、`map`、指针字段仍然引用原来的底层数据。一个请求修改副本，可能把所有请求共享的模板一起改掉。

## 浅拷贝为什么危险

```go
package main

import "fmt"

type Policy struct {
    Rules  []string
    Labels map[string]string
}

func main() {
    origin := Policy{
        Rules:  []string{"allow-login"},
        Labels: map[string]string{"env": "prod"},
    }

    clone := origin // 只复制 slice/map 的描述符
    clone.Rules[0] = "deny-login"
    clone.Labels["env"] = "test"

    fmt.Println(origin.Rules[0])       // deny-login
    fmt.Println(origin.Labels["env"]) // test
}
```

`Policy` 这个 struct 本身被复制了，但 `Rules` 和 `Labels` 的底层数据仍然共享。

因此原型模式的重点不是 `Clone()` 这个名字，而是**明确复制语义**。

## 一个更完整的 Go 实现

下面用一个多租户策略模板作为示例。

```go
package policy

import (
    "maps"
    "slices"
)

type Rule struct {
    Name     string
    Enabled  bool
    Metadata map[string]string
}

type Policy struct {
    TenantID string
    Version  int64
    Rules    []Rule
    Labels   map[string]string
}

func (p *Policy) Clone() *Policy {
    if p == nil {
        return nil
    }

    cloned := &Policy{
        TenantID: p.TenantID,
        Version:  p.Version,
        Labels:   maps.Clone(p.Labels),
        Rules:    slices.Clone(p.Rules),
    }

    // slices.Clone 只复制 []Rule；Rule 内部还有 map，所以继续复制一层。
    for i := range cloned.Rules {
        cloned.Rules[i].Metadata = maps.Clone(p.Rules[i].Metadata)
    }

    return cloned
}
```

这里故意不用反射或 JSON 序列化做通用深拷贝，因为显式 `Clone` 有几个好处：

- 哪些字段共享、哪些字段复制，一眼就能看出来；
- 编译器能帮助你发现字段变化；
- 没有序列化开销；
- 可以针对大对象做 copy-on-write 优化。

## 使用方式

```go
base := &policy.Policy{
    TenantID: "default",
    Version:  12,
    Rules: []policy.Rule{
        {
            Name:    "rate-limit",
            Enabled: true,
            Metadata: map[string]string{
                "limit": "100",
            },
        },
    },
    Labels: map[string]string{"env": "prod"},
}

// 新租户不需要重新从数据库读取、解析、编译整套规则。
tenantPolicy := base.Clone()
tenantPolicy.TenantID = "tenant-42"
tenantPolicy.Rules[0].Metadata["limit"] = "200"
```

原型对象负责提供一个“已经初始化好的起点”，调用方只覆盖真正不同的部分。

## 一定要测“副本是否独立”

```go
func TestPolicyCloneIsIndependent(t *testing.T) {
    origin := &Policy{
        TenantID: "default",
        Rules: []Rule{{
            Name:     "rate-limit",
            Enabled:  true,
            Metadata: map[string]string{"limit": "100"},
        }},
        Labels: map[string]string{"env": "prod"},
    }

    cloned := origin.Clone()
    cloned.Rules[0].Metadata["limit"] = "200"
    cloned.Labels["env"] = "test"

    if got := origin.Rules[0].Metadata["limit"]; got != "100" {
        t.Fatalf("origin metadata was modified: %s", got)
    }
    if got := origin.Labels["env"]; got != "prod" {
        t.Fatalf("origin labels were modified: %s", got)
    }
}
```

原型模式的单元测试应该关注**隔离性**，而不仅仅是“字段值相等”。

## 哪些字段反而应该共享？

深拷贝不是越深越好。

例如：

```go
type Policy struct {
    CompiledMatcher *regexp.Regexp
    Rules           []Rule
}
```

如果 `CompiledMatcher` 构造非常昂贵，而且对象本身是并发安全、不可变的，那么副本完全可以继续共享它。

```go
cloned.CompiledMatcher = p.CompiledMatcher
```

这其实才是原型模式最有价值的地方：

```text
昂贵且不可变的数据 ───────────► 共享

会被副本修改的数据 ──────────► 深拷贝
```

## Go 里常见的实现选择

### 1. 手写 Clone：首选

适合领域对象和核心数据结构。语义清晰，可维护性最好。

### 2. `maps.Clone` / `slices.Clone`

适合浅层容器，但要记住元素内部如果还有引用类型，仍然需要继续处理。

### 3. 序列化再反序列化

```go
raw, _ := json.Marshal(src)
_ = json.Unmarshal(raw, &dst)
```

代码少，但性能差、错误处理麻烦，还会把“复制语义”藏起来。一般只适合低频工具代码，不建议用在热路径。

### 4. 反射型通用 DeepCopy

看起来省代码，长期维护往往最麻烦：channel、func、未导出字段、自定义资源句柄都很难有统一正确语义。

## 什么时候值得使用

适合：

- 创建对象要经过数据库、RPC、文件或昂贵计算；
- 大部分新对象和模板相同，只改少数字段；
- 已经存在一个经过校验或编译的模板对象；
- 测试中需要快速生成“基线对象 + 少量差异”。

不适合：

- 普通小 struct，直接字面量构造更清楚；
- 对象拥有数据库连接、锁、文件描述符等不能随意复制的资源；
- 对象关系非常复杂，却没有明确的复制边界；
- 复制成本和重新创建成本差不多。

## 和其他模式的区别

| 模式 | 关注点 |
|---|---|
| 工厂模式 | 根据输入决定创建哪一种对象 |
| 建造者模式 | 分步骤、带约束地创建复杂对象 |
| 原型模式 | 基于一个已经存在的对象快速复制 |

## Go 工程里的判断标准

看到 `Clone()` 不代表你用了好的原型模式。更重要的是回答三个问题：

1. **为什么重新创建很贵？**
2. **哪些字段可以安全共享？**
3. **哪些字段必须复制才能保证修改隔离？**

这三个问题如果说不清楚，通常还不需要引入原型模式。
