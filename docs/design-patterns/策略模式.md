# 策略模式 Strategy

> **核心思想：**把可以互相替换的算法封装成稳定契约，让业务流程不再依赖一大串 `if/else`。

Go 里策略模式经常不需要一个 struct + interface；如果策略是无状态单操作，**函数类型就是最自然的策略对象**。

## 场景：订单折扣算法

```go
type Order struct {
    Amount int64
    Items  int
}

type DiscountStrategy func(context.Context, Order) (int64, error)
```

不同策略：

```go
func NoDiscount(_ context.Context, order Order) (int64, error) {
    return order.Amount, nil
}

func Percentage(percent int64) DiscountStrategy {
    return func(_ context.Context, order Order) (int64, error) {
        if percent < 0 || percent > 100 {
            return 0, errors.New("invalid discount percent")
        }
        return order.Amount * (100 - percent) / 100, nil
    }
}

func Threshold(threshold, reduce int64) DiscountStrategy {
    return func(_ context.Context, order Order) (int64, error) {
        if order.Amount < threshold {
            return order.Amount, nil
        }
        total := order.Amount - reduce
        if total < 0 {
            total = 0
        }
        return total, nil
    }
}
```

Checkout 只依赖策略：

```go
type Checkout struct {
    discount DiscountStrategy
}

func (c Checkout) Total(ctx context.Context, order Order) (int64, error) {
    return c.discount(ctx, order)
}
```

选择策略的职责放在 composition root：

```go
strategy := NoDiscount

switch campaign.Type {
case "vip":
    strategy = Percentage(10)
case "full-reduction":
    strategy = Threshold(10000, 2000)
}

checkout := Checkout{discount: strategy}
```

## 策略带状态或多个方法时再用接口

```go
type RetryStrategy interface {
    Next(attempt int) (delay time.Duration, retry bool)
    Reset()
}
```

如果一个策略需要多个协同行为、内部状态或生命周期，接口比函数类型更合适。

## 不要把选择逻辑塞回 Context

反例：

```go
func (c Checkout) Total(order Order) int64 {
    switch c.campaign.Type {
    // 又回到 if/switch
    }
}
```

这样虽然定义了 Strategy 类型，真正的策略选择仍然和业务流程耦合。

## 测试每种算法的边界

```go
func TestThreshold(t *testing.T) {
    strategy := Threshold(10000, 2000)

    tests := []struct {
        amount int64
        want   int64
    }{
        {9999, 9999},
        {10000, 8000},
        {15000, 13000},
    }
    // ...
}
```

策略非常适合 table-driven tests，因为每个算法都应该是小而独立的单元。

## 和 Factory 搭配

Factory 可以负责根据配置创建 Strategy：

```text
config -> strategy factory -> DiscountStrategy -> Checkout
```

Factory 决定“用谁”，Strategy 决定“怎么算”。

## 什么时候别用

只有两个简单分支且几乎永远不变：

```go
if vip { ... } else { ... }
```

往往比引入一套策略体系更清楚。模式的目标是控制变化，不是消灭所有 `if`。
